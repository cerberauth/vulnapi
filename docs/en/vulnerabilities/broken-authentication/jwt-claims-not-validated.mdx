A valid signature only proves who signed the token. The API must also require the claims it relies on: the issuer (`iss`), the audience (`aud`), the subject (`sub`), the validity window (`exp`, `nbf`, `iat`), and the scope or role granting access to the operation.

## Example

A token carrying a scope:

```json
{
  "iss": "https://idp.example.com",
  "aud": "api",
  "sub": "1234567890",
  "scope": "orders:write",
  "exp": 1516242622
}
```

The same token re-signed without `aud` and `scope` must be rejected. If the API accepts it, it does not validate these claims.

## How to test?

`jwt.claim_removal` re-signs the token without `iss`, `aud`, `sub`, `exp`, `nbf` and `iat`, one at a time and all together. `jwt.scope_not_validated` re-signs it without its `scope`, `scp`, `roles`, `role`, `groups`, `permissions` and `authorities` claims. Both need the signing secret, cracked by `jwt.weak_secret` or passed with `--jwt-secret`, and are skipped otherwise.

## What is the impact?

An API that ignores these claims accepts tokens issued for another API or tenant, tokens without subject or expiry, and tokens stripped of their permissions, which leads to impersonation and privilege escalation.

## How to remediate?

- Configure the JWT library to require `iss`, `aud`, `sub` and `exp`, with the expected issuer and audience values.
- Reject tokens missing a required claim instead of treating it as optional.
- Authorize each operation against the scope or role claims, and deny access when they are absent.
