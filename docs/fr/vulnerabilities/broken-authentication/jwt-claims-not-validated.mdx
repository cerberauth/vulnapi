---
title: Claims JWT non validés
description: Une vulnérabilité où le serveur accepte un JWT correctement signé dont les claims enregistrés, de scope ou de rôle ont été supprimés.

Une signature valide prouve seulement qui a signé le token. L'API doit aussi exiger les claims sur lesquels elle s'appuie : l'émetteur (`iss`), l'audience (`aud`), le sujet (`sub`), la période de validité (`exp`, `nbf`, `iat`) et le scope ou le rôle donnant accès à l'opération.

## Exemple

Un token portant un scope :

```json
{
  "iss": "https://idp.example.com",
  "aud": "api",
  "sub": "1234567890",
  "scope": "orders:write",
  "exp": 1516242622
}
```

Le même token re-signé sans `aud` ni `scope` doit être rejeté. Si l'API l'accepte, elle ne valide pas ces claims.

## Comment tester ?

`jwt.claim_removal` re-signe le token sans `iss`, `aud`, `sub`, `exp`, `nbf` et `iat`, un par un puis tous ensemble. `jwt.scope_not_validated` le re-signe sans ses claims `scope`, `scp`, `roles`, `role`, `groups`, `permissions` et `authorities`. Les deux nécessitent le secret de signature, cassé par `jwt.weak_secret` ou passé avec `--jwt-secret`, et sont ignorés sinon.

vulnapi scan curl [url] -H "Authorization: Bearer eyJhbGciOiJIUzI1NiI..." --jwt-secret [secret] --scans "jwt.claim_removal" --scans "jwt.scope_not_validated"

## Quel est l'impact ?

Une API qui ignore ces claims accepte des tokens émis pour une autre API ou un autre tenant, des tokens sans sujet ni expiration, et des tokens privés de leurs permissions, ce qui mène à l'usurpation d'identité et à l'élévation de privilèges.

## Comment corriger ?

- Configurez la bibliothèque JWT pour exiger `iss`, `aud`, `sub` et `exp`, avec les valeurs d'émetteur et d'audience attendues.
- Rejetez les tokens auxquels il manque un claim requis au lieu de le traiter comme optionnel.
- Autorisez chaque opération selon les claims de scope ou de rôle, et refusez l'accès quand ils sont absents.
